## 3. Mechanism: why not inspect.getsource

Evaluated against four criteria; rejected on two, then measured the alternative.

                                raw getsource  AST-normalized  bytecode   behavioural probe
comment/reflow/docstring edit   MOVES (false)  invariant       invariant  invariant
needs .py at runtime            YES            yes             no         NO
stable under -O / -OO           yes            yes             NO (-OO)   YES
stable across CPython versions  yes            NO (ast.dump)   NO         YES
coverage                        total          total           total      probe-limited (mitigated)

(a) Over-sensitivity, measured. Comment-only edit inside build_host_map, no behaviour change:
      behavioural digest     : 6f6f8b856d9ae500 -> 6f6f8b856d9ae500   moved=no
      inspect.getsource hash : 22dbbd37357355b4 -> c9647e78d9729965   moved=YES
    A fingerprint that fires on cosmetics invalidates every published host-map hash on a typo fix.
    Readers learn to ignore it and maintainers re-bless reflexively -- the same failure the gate
    exists to prevent, arriving by another route.

(b) Source availability, measured. getsource DOES work from a wheel and from zipimport
    (zipimporter implements get_source), so those two concerns from the brief do not bite. It
    raises on a bytecode-only install:
      removed 72 .py files, kept .pyc only
      loaded from: .../sourceless/cmig/core/host_map.pyc
      behavioural digest  : sha256:6f6f8b856d9ae50070edd865f8c7763620c8e56ab00b4631745b75cd2092667f
      inspect.getsource   : OSError - could not get source code
    This matters because of P4's own design choice: the envelope golden was shipped inside the
    package "so the gate runs wherever the tests run, rather than skipping on a trimmed checkout."
    A fingerprint that raises on a trimmed install reintroduces exactly that hole -- worse, at
    manifest-emission time rather than gate time.

    And -O / -OO:
      default: sha256:6f6f8b856d9ae50070edd865f8c7763620c8e56ab00b4631745b75cd2092667f
      -O     : sha256:6f6f8b856d9ae50070edd865f8c7763620c8e56ab00b4631745b75cd2092667f
      -OO    : sha256:6f6f8b856d9ae50070edd865f8c7763620c8e56ab00b4631745b75cd2092667f

WHAT I DID INSTEAD: measure the matcher rather than read it. cmig/core/host_map_probe.py runs the
REAL build_host_map and the REAL id normalizer over a frozen synthetic host and two-member pool,
and hashes everything they produced -- counts, every field of every entry (including the
suggestion strings that reach host_exchange_map.csv), the warnings, and a 22-element
id-normalization vector. The digest goes into map_spec["match_behavior"].

The stubs are duck-typed (build_host_map only reads .exchanges/.reactions/.id/.metabolites/
.lower_bound/.upper_bound/.annotation), so the probe needs no cobra and costs microseconds. It is
deliberately UNCACHED -- a cache would hand a stale answer to the tests that verify the digest
tracks the implementation.

The cost of this mechanism is coverage, and I paid it explicitly. The probe fixture is built
case-by-case from the verifier's own ten-perturbation matrix, one designed case per decision
point, and test_the_probe_fixture_still_distinguishes_every_decision_point asserts each case still
bites -- narrowing the fixture fails a test rather than quietly narrowing the guarantee. That test
earned its keep immediately: my first fixture had no metabolite reachable by BOTH annotation and
normalized, so a pure HOST_MAP_MATCH_ORDER reorder did not change probe output and the test
failed. I added `ord_e` (the exact shape of the real D/L break) and it bites.

I also made the four inert fields LOAD-BEARING, so the manifest stops asserting things it does not
enforce: HOST_MAP_MATCH_ORDER now drives the strategy loop, HOST_MAP_SECRETION_CRITERION names a
predicate in a table that build_host_map looks up, HOST_MAP_ANNOTATION_SOURCES drives the
annotation index build, and HOST_MAP_ANNOTATION_REQUIRES_UNIQUE_TARGET drives the uniqueness test.
annotation_sources' recorded strings are rendered from the new structured constant, so that
field's serialized value is byte-identical to before.

Two map_spec fields remain descriptions (match_policy_version, and id_normalization's
uppercase_stereoisomer_suffix_folded / case_folded). They are now labelled as such in the
docstring, and they ARE covered by the digest -- the id vector contains lac__D_e / lac__L_e /
ste__d_e / MixedCase_e, so a change to either behaviour moves the hash.

## 2. What I built: result_digest

`cmig/core/workflow_manifest.py` — `artifact_result_digest(out_dir, kind, artifacts)`: sha256 over
the artifact bytes a run produced, plus a per-artifact breakdown and an explicit
`missing_artifacts` list (a run that failed to write half its outputs must not digest the same as
one that wrote them all). Emitted for every workflow kind by `write_workflow_manifest`, so both
surfaces — `cli.main._emit_workflow_manifest` and `publication_benchmark._BundleRecorder.emit` —
get it without a second code path.

ADDITIVE, exactly as directed. `result_digest` is not in `components` and not in `hash_components`;
`compute_workflow_hash` is untouched. Pinned by
`test_the_result_digest_is_additive_and_never_enters_the_input_hash`: two runs with wildly
different artifacts produce the same run_hash, and the recomputed hash still equals it.

`cross_run_comparable` is a *measured* claim, not an assumption: true only for kinds whose
artifacts have been verified byte-deterministic across two real runs. Currently `host_map` only
(verified: identical result_digest and byte-identical manifest across two runs). Unlisted kinds
still get a digest and are still checked by inspect-run; they are simply not advertised as
diffable across runs, because a figure raster or a parquet write id would manufacture false alarms.

`cmig/cli/main.py` — `_verify_result_digest` recomputes from the files on disk; `inspect-run`
reports it and names which claim failed:

  result_digest: sha256:4521ad31…   (certifies the ARTIFACT BYTES) — verified

  ... and on a tampered run, to stderr:
